# 1. Project Overview
## Project Name
DramaRadar（吵架雷達）

## Project Description
本專案旨在建立一套 **商圈輿情分析平台**。

系統透過 Apify Actor `compass/crawler-google-places` 搜尋特定縣市店家，蒐集店家基本資訊，再利用 Apify Actor `compass/google-maps-reviews-scraper` 抓取公開評論，經過資料清洗與 AI 分析後，將分析結果儲存至 PostgreSQL，最後提供 Dashboard 視覺化分析與 Threads 自動發文功能。

目標並非單純爬取評論，而是建立一套完整且可持續運行的資料分析 Pipeline，提供使用者快速掌握輿情、潛在問題店家，滿足大眾吃瓜心態。

# 2. Background
目前 Google Maps 雖提供店家資訊與評論，但缺乏：

* 大量資料分析能力
* 具爭議性的評論整理
* AI 摘要分析
* 自動化每日追蹤

使用者若想分析一整個商圈，仍須逐間店家查詢，效率極低。
因此建立一套自動化平台，降低人工搜尋成本，提升資料分析效率。

# 3. Project Goal
本專案主要目標如下：

* **Goal 1：建立自動化店家資料蒐集流程。**
* **Goal 2：建立評論蒐集與清洗流程。**
* **Goal 3：利用 AI 自動分析評論內容。**
* **Goal 4：提供 Dashboard 進行視覺化分析。**
* **Goal 5：建立每日自動更新 Pipeline。**
* **Goal 6：透過 Threads 自動發布分析內容。**

# 5. Design Principles (開發原則)
1. Contract First Development：所有資料格式須先完成定義，再開始程式開發。
2. Single Source of Truth：所有正式資料皆以 PostgreSQL 為唯一資料來源。
3. Domain-Oriented Design：每個 Domain 僅負責單一職責，僅能寫入自己擁有的資料表。
4. MVP First：重要的先做，再逐步擴充功能。
5. Remote Friendly：所有文件皆存放於本 repo 的 `docs/` 目錄，隨程式碼一起版本控管，任何成員皆可隨時查閱。
6. Code Review Required：所有程式皆須透過 **Pull Request** 審核後才能合併。
7. Development：所有開發環境統一使用 Docker（Dev Containers）。

# 6. Constraints (約束條件)
1. Project Duration：5-6週
2. Team：5人
3. Development Mode：Remote。
4. Budget：開發時須控制 API 使用成本。Apify 與 Gemini 皆為按量計費，店家蒐集不列入每日排程，改為需要時手動觸發。
5. MVP Deadline：2026/08/15

## 範圍限制

MVP 階段刻意收斂的範圍，均為成本與資料品質考量：

* **地區**：僅台北市。搜尋以 12 個郵遞區號執行，Dashboard 亦以 `store.address` 含「台北市／臺北市」過濾。
* **業種**：僅餐飲類（餐廳、小吃、麵店、便當、餐酒館、料理）。
* **店家**：評論數 ≥ 30 且（總分 ≤ 4.3 或一星佔比 ≥ 10%）且營業中，才會納入追蹤。
* **評論**：僅保留 1~2 星評論。
* **AI 分析**：僅分析**已有老闆回覆**的評論 — 沒有雙方交鋒就沒有分析價值。
* **連鎖店**：命中連鎖品牌黑名單、或老闆回覆與制式公關話術相似度 ≥ 80% 的店家，會被標記為不再抓取評論。
